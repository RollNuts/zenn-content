関数を変えたので、AIにレビューを頼みたい。ただし、ソースコードもファイル名も社外には送れない。そこで「F02がF01を呼んでいます」とだけ伝えたとします。これで、次にどんなテストを書けばよいでしょうか。

同じ関数に二通りの変更を加えて試すと、この問いの難しさが見えます。どちらも呼び出し元は同じ。それでも、実際に壊れたのは別々の場所でした。

| 定義に加えた変更 | 引数を省略する呼び出し | 戻り値に1を足す呼び出し |
| --- | --- | --- |
| 変更前 | 通る | 通る |
| A：省略できた引数を必須にする | `TypeError` | 通る |
| B：数値だった戻り値を文字列にする | 通る | `TypeError` |

クラウドに渡す候補をファイル間の関係だけにすると、AもBも**まったく同じJSON**になりました。AIは一般的なテストを列挙できます。でも、この入力には「今回はどちらを先に確かめるべきか」を選ぶ材料がありません。逆に「戻り値が数値から文字列に変わる」という一文を出せるなら、実名を一つも渡さずに、ずっと具体的な相談ができます。

この記事では、まず手元でこの境目を再現します。その上で、コードを端末に残し、足りない推論だけをクラウドへ頼むなら、**どこで外部への相談をやめるか**を考えます。

:::message
Microsoft × Zenn「私の考えるハイブリッドLLM～実践と構想～」の構想部門向けです。Pythonの二つの変更と、後述する公開コードの関係照会は手元で検証できます。Surface Laptop Ultraは所有しておらず、ローカルLLMとクラウドLLMを結ぶ部分はこれから試したい設計です。
:::

## 一行ずつ情報を戻すと、どこで二つを見分けられるか

冒頭の表は、公開用に作った小さなPythonの例を実行した結果です。GitとPython 3.12があれば、次のコマンドで同じ出力を確認できます。取得後の実行にはパッケージの追加、APIキー、モデルは要りません。

```sh
git clone https://github.com/RollNuts/zenn-content.git zenn-boundary-demo
cd zenn-boundary-demo
git checkout --detach 4e1a102c95844a4a7052d4c4123bf73f7b895003
python3.12 -B examples/hybrid-send-boundary/compare.py
```

出力の前半は端末内のテスト結果、後半は「もし送るとしたら」の候補です。プログラムはどの候補も送信しません。

```text
Local checks before: omit_argument=ok, add_one_to_result=ok
Local checks A: omit_argument=TypeError, add_one_to_result=ok
Local checks B: omit_argument=ok, add_one_to_result=TypeError
```

後半の `A == B` は、**二通りの変更から作った送信候補の値が一致するか**を表します。二つのテストは同じファイルから同じ定義を呼ぶため、ファイル単位の関係は1件です。

| 候補に含めたもの | この例でAとBに差が出たか |
| --- | --- |
| 何も許可しない | どちらも候補なし（`null`） |
| 関係の件数 | どちらも `{"relations": 1}` |
| 呼び出し元と定義の仮名 | どちらも `{"caller": "F02", "definition": "F01"}` |
| 仮名に契約変更のメモを加える | Aは「引数が必須に」、Bは「戻り値が文字列に」と区別できる |

メモはこの教材の入力として人が付けました。テスト結果を見てから正解を推測するモデルも、契約変更を自動抽出する処理も入っていません。ここで確認できたのは、情報の削り方によって異なる変更が同じ入力に見える、という一点です。[固定版のコードと全出力](https://github.com/RollNuts/zenn-content/tree/4e1a102c95844a4a7052d4c4123bf73f7b895003/examples/hybrid-send-boundary)

## 「本文を持たない」コードグラフに何が残ったか

この問いの出発点は、私がGitのコンフリクトに困って作り始めたVeripsa Coreです。変更同士の関係を調べるため、ソース本文を入れずに、ファイルやコマンドのつながりを取り出せるようにしました。ところが、そのデータを外に渡そうとすると、本文を除いた後にも読むべき箇所がありました。

公開のTauriサンプルから取り出した固定データを、必要な部分だけ抜き出します。

```text
src-tauri/commands.rs  ── alters  ──▶  tauri_command::receipt_label
src/client.ts          ── queries ──▶  tauri_command::receipt_label
```

このデータには、二つのファイルが同じコマンドを介してつながる証拠があります。ソースの行は一つもありません。それでも、何の機能らしいか、どの言語の境界をまたぐかは名前から読めます。仮名に置き換えた後も、珍しい関係の組み合わせや件数が手掛かりになり得ます。[固定した関係データ](https://github.com/RollNuts/zenn-content/blob/6c3ef33ab0074ab7895602c46994e98c3d186bca/examples/core-local-mcp/demo/official-literal.json)

この関係は、ローカルMCPの `tauri_related_files` から照会できます。固定した4例では、公式APIでリテラルのコマンド名を渡す例は1件・`observed`、同名の自作関数と動的な名前の例は0件・`not_observed`、同名定義が二つある例は2件・`uncertain` でした。0件だったときに「ほかに呼び出し元はない」と伝えてしまうと、受け手は調査を打ち切ってしまいます。クラウドへの質問にも、どの版・範囲で何が未確認かを残したい理由です。[モデルなしで試せるMCP照会と4例の結果](https://github.com/RollNuts/zenn-content/blob/6c3ef33ab0074ab7895602c46994e98c3d186bca/examples/core-local-mcp/README.md)

問い合わせ実装は、起動時に読むsnapshotを5 MiB、返す関係を最大20行、結果のJSON本文を32 KiBに制限しています。短いパスや識別子なら、その上限に十分収まります。出力サイズだけを制約しても、何を外へ渡せるかは決まりません。MCPはここでは問い合わせの入口です。ホスト型GitHub Appは2026年8月18日から停止しており、この手順にサーバーは使いません。Core本体のライセンスはBSL 1.1です。[問い合わせの実装](https://github.com/RollNuts/zenn-content/blob/6c3ef33ab0074ab7895602c46994e98c3d186bca/examples/core-local-mcp/query_service.py)・[Coreの提供状況](https://github.com/RollNuts/veripsa)

## 一問を送るか、端末で調べるか

では、冒頭のBで、契約変更の要約までは送ってよいとします。私なら、クラウドへ頼む仕事を次の一問に絞ります。これはモデルに送る前の相談文の例です。

> 版S1でF02がF01を呼ぶ関係を確認した。F01の戻り値は数値から文字列になる。F02が結果をどう使うかは未確認。この変更で失敗しうる使い方を一つ挙げ、それを端末で確かめる最小のテストを提案してほしい。

例えば「数値として加算している箇所を確かめる」という案が返れば、手元の対応表でF02を開きます。教材の `add_one_to_result` はまさに戻り値へ1を足しており、Bでだけ失敗します。ここで動かしたのはローカルのテストです。モデルがその案を出したという実験結果ではありません。対象版が変わった場合や、返答に対応表にないIDが混じった場合、その案の参照先は改めて確認します。

一方で、**契約の要約も、関係の存在も送れない**ことがあります。この場合、クラウドへの質問は作りません。同じ対応表からF02を開き、手元のテストを実行すれば、作業は進みます。Tauriの公開例でも、抽出結果に残っていない引数の値は、元の呼び出し側を見ると `{ count: 3 }` と確認できます。これはその1か所についての事実で、ほかの経路まで調べ終わったことにはなりません。[実際の呼び出し側](https://github.com/RollNuts/zenn-content/blob/6c3ef33ab0074ab7895602c46994e98c3d186bca/examples/tauri-command-contract/fixtures/official-literal/src/client.ts#L4)

## Surfaceとクラウドに、それぞれどの仕事を頼むか

Surface Laptop Ultraがあれば、まず公開サンプル一つを使い、次の一往復を試したいです。

| 場所 | 任せる仕事 | そこで保持するもの |
| --- | --- | --- |
| 端末 | 関係を取り出す。ローカルLLMで変更点・不明点の候補を作り、元のコードと照合する | ソース、実名対応表、根拠の行、詳しいテスト結果 |
| 送信の直前 | モデルとは別の処理で、事前に許した項目・値だけを採用する。残った情報で質問を区別できなければ端末で続ける | 許可条件と対象版。生成した自由記述をそのまま送る経路は設けない |
| クラウド | 許可済みの一問から、別の検査案を提案する | その問い合わせに必要な仮名・関係・契約の要約 |
| 再び端末 | 提案を元の版と実ファイルへ戻し、テストで確かめる | 採用した検査と実行結果 |

ローカル候補はopen-weightの [gpt-oss-20b](https://developers.openai.com/api/docs/models/gpt-oss-20b)、クラウド候補は [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) です。普段の整理を端末に置けば、元のコードを開いたまま何度でも問いを作り直せます。その代わりにモデルを載せるメモリ、待ち時間、電力、更新の手間を負います。クラウドには、端末側でまだ解けず、送信できる形に整えられた問いだけを渡したい。授受する情報が少なすぎれば、その一回にも費用をかける理由はありません。特定のSurfaceでの速度や品質、API利用額は未測定です。

公開の[公式参考キットにあるUC1](https://github.com/dahatake/Surface-Laptop-Ultra-RTX-Spark-Vibe-Coding-kit#uc1-private-by-default-fusion機密コードを外に出さずに-vibe-coding-する)にも、生のコードを端末に残す構成があります。そこで試してみたいのが、その**要約からさらに何を消したら、異なる変更が見分けられなくなるか**です。

実機では同じ合成課題をローカルだけの場合と両方を使う場合で比較し、同じ公開入力を渡したクラウドだけの結果も参照します。最初に見るのは、禁止した識別子が実際の送信内容に現れないか、拒否した時に通信が発生しないか。その次に、追加提案を実ファイルへ戻せたか、失敗するテストにたどり着いたか、手元の検索とテストだけの時より人の確認時間が減ったかを測ります。端末の待ち時間・電力とクラウドの入出力トークンも並べ、改善が持ち出す情報と追加費用に見合うかを判断します。許可外の送信が1件でもあればその構成は採用しません。この小例のように手元の2テストで答えが出るなら、そこで終了です。

自分の現場で試すなら、最近の変更を二つ思い浮かべてください。**ファイル名も変更理由も伏せたとき、その二つは相手に同じ質問に見えませんか。** もし同じに見えたら、違いを伝える一文を書き出す。その一文を出せるなら相談の出発点にできるし、出せなければ、先に端末で試すべきテストが見えてきます。
