> Microsoft × Zenn「私の考えるハイブリッドLLM～実践と構想～」構想部門向け。実機のSurface Laptop Ultraや高性能GPU PCは未所有。ローカル／クラウドLLMの実行・性能比較は未実施です。

## デプロイ成功の表示と、読者が見た内容は違う

GitHubの変更が反映された。デプロイの画面も成功になった。そこでAIが「公開できました」と報告したとしても、読者のブラウザーに新しい本文が届いているとは限らない。古いHTMLが残っていたり、配信の一部だけ新しくなったりするからだ。

私が考えるハイブリッドLLMは、制作を支援するモデルと、**公開完了を判定する検査**を分ける。接続がない時間はローカルLLMで草稿・ログ・確認候補を整理する。接続できるときだけ、必要ならクラウドLLMで難しい表現や設計をレビューする。しかし最後の「完了」はモデルに言わせない。revisionと代表HTMLのような観測値を、決定的なルールで比較する。

```text
手元の草稿・ログ
       ↓
ローカルLLM: 要約・チェック候補・未確認の整理
       ↓
接続あり？ ── なし → 草稿と確認待ちを保持
       │
       └─ あり → 必要時のみクラウドLLMが表現/設計をレビュー
                       ↓
                公開処理（別システム）
                       ↓
          配信revision + 代表HTMLを取得
                       ↓
              決定的なvalidator
             ├─ 不一致 → 未完了・差分を表示
             └─ 一致   → 検査範囲内で確認済み
```

クラウドLLMと普通のvalidatorを並べただけでは、私の言うハイブリッドLLMにはならない。**ローカルLLMがオフラインでも意味のある仕事をし、接続条件によって経路が変わり、失敗時には保留する**ことが必要だ。

## すでにある最小の配信検査

この構想の中心は、[公開したPythonの最小例](https://github.com/RollNuts/zenn-content/blob/2f51517aa4d7d29013146eb7e93e43c0c3d7b2c3/examples/deployment-revision/README.md)と[test_check_release.py](https://github.com/RollNuts/zenn-content/blob/2f51517aa4d7d29013146eb7e93e43c0c3d7b2c3/examples/deployment-revision/test_check_release.py)だ。Python 3.12の標準ライブラリとloopback通信だけで動く。引継ぎ済みの再検証では**13 tests OK**。今回、私が新たにコードを動かしたわけではない。

この例では、HTTP 200という応答コードだけで完了とせず、期待するrevisionと、代表HTMLに埋めた識別子が一致するかを調べる。

| 配信状態 | HTTP | 判定 |
| --- | --- | --- |
| 旧版Aのまま | すべて200 | 拒否 |
| markerはB、HTMLはA | すべて200 | 拒否 |
| markerもHTMLもB | すべて200 | 受理 |

大事なのは「全HTTP 200」でも最初の二つは拒否されることだ。これは、**少なくとも確認対象の応答に期待版が現れたか**を判定する小さな検査であり、全ページの一致、JavaScript実行、配信成果物の真正性を証明するものではない。ブラウザーのキャッシュやCDNの全経路まで網羅したと書くべきでもない。

この例の観測はローカルHTTPの合成環境に対するものだ。実サービスの公開事故を再現したという主張でも、LLMが不具合を発見したという実測でもない。

## ローカルLLMに任せたい仕事

ローカルの候補は [gpt-oss-20b](https://developers.openai.com/api/docs/models/gpt-oss-20b)。テキストを扱うopen-weightモデルなので、草稿、作業ログ、失敗時の差分を端末内で整理する用途を検討できる。ただし、対象Surface上での動作、必要メモリ、電力、温度、処理時間は未検証で、モデルを入手・実行したことはない。

ローカルLLMは「公開前に何を確かめるか」のチェック候補を作り、どの証拠が未取得かを示す。例えば、HTMLの期待見出し、公開日、revisionの一致、代表ページの取得失敗を整理する。接続がなければ、確認待ちのリストを保持する。取得できないものを成功と推測しない。

クラウド候補の [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) には、表現の分かりやすさ、仕様の矛盾、設計の抜けをレビューさせる構想だ。通信が使えるときに、送信が許可された最小の草稿や要約だけを渡す。従量APIの利用は既存のChatGPT/Codex契約枠と同一ではない。今回は呼び出しも課金も行わない。

クラウドが応答しなくても、ローカルの下書き整理と決定的な公開検査は続けられる。一方、公開先のHTTP応答が取得できなければ、**公開完了は保留**にする。LLMが「たぶん成功」と書いたら、その回答を報告へ採用しない。

## 「完了」を何段階に分けるか

例えば運用上の状態を次のように分ける。

```text
draft_ready
  → source_updated
  → deployment_reported
  → delivery_verified
  → review_completed
```

`source_updated` はソースが変わっただけ、`deployment_reported` は配信側が処理を報告しただけ。`delivery_verified` は指定したrevisionと代表HTMLの一致を実際に確認した状態であり、全経路保証ではない。`review_completed` は内容の独立レビューを別に終えた状態だ。

モデルが作る説明文は、各状態の根拠URL・取得時刻・期待値・実測値に紐づける。取得失敗や不一致があれば状態を先へ進めない。何をもって完了とするかを先に決めておくことで、AIの流暢な報告と実際の配信状態を切り離せる。

## 別の方式を選ぶなら

cloud-onlyはレビュー能力を集中させやすいが、オフラインでは作業できず、送信範囲や従量料金も課題になる。local-onlyはネット接続なしで文章やログを整理できるが、端末性能とモデルの精度に依存する。hybridは接続時に高度なレビューを追加できる一方、切替と同期の管理が必要になる。

ただし、**公開判定だけが目的ならLLMなしのvalidatorが最も単純**だ。私の案は、制作中の曖昧な判断や確認候補の整理にはモデルを使い、完了判定には使わない。モデルを増やすほど良いという主張ではない。

## 実機入手後に試す最小実験

OS、モデル版、量子化、ランタイム、温度、固定した入力草稿・ログを記録する。接続あり／なしを切り替え、同じ入力でcloud-only、local-only、hybridを比較する。配信状態は既存の3パターン（旧版A、混在、B一致）を用い、さらに取得失敗とクラウドタイムアウトを加える。

最低限の合格条件は、旧版Aと混在状態を**完了扱いしない**こと、B一致だけを定義した検査範囲内で受理すること、接続断やクラウド障害で未確認を成功へ昇格させないことだ。ローカルLLMのチェック候補が不適切なら人が却下でき、モデルを使わなくてもvalidatorは同じ判定を返す必要がある。

人の確認時間、誤った完了報告、保留率、再試行、クラウド入出力トークンを測り、端末の電力・保守負担も別に記録する。モデル性能やコスト削減率は未測定で、数値を予告しない。

この構想でAIに任せたいのは「何を確認すべきかを考える仕事」までだ。**「確認した」という事実は、取得した証拠と判定条件からしか生まれない。** ハイブリッドLLMの価値を、生成の便利さではなく、失敗を失敗として止められる運用に置きたい。
