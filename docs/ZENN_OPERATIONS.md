# Zennの編集・公開運用

## 対象と基本方針

- 対象は `RollNuts/zenn-content` と Zenn `veripsa`。2026年11月12日の依頼「zennを運用して、記事投稿して」に基づく。
- Git、Python、静的サイト、コード解析など、本人の公開プロジェクト・実際の実装・検証記録を題材にする。
- 追加費用は0円。既存の環境と無料の公開手段を使い、有料API、追加クレジット、従量課金を導入しない。
- 1記事につき読者の疑問を1つに絞る。既存記事と同じ説明を新作へ分割せず、既存記事の改善が適する場合は改稿する。
- 本人が経験していない体験、測っていない数値、未公開機能の利用実績を作らない。エージェントが実行した検証はそのように扱い、AI補助の開示を維持する。

## 点検枠

火曜・土曜の19時ごろ（Asia/Tokyo）を基本とする。1回につき新規公開は最大1本。枠が来ても、題材・検証・独自の知見が不足する場合は既存原稿の改善に使う。

新しい公開・予約は、直近の公開または予約作成から25時間以上空いている場合だけ試す。これは余裕を持たせた独自の運用基準であり、Zennの投稿可能数や解除時刻を保証しない。

## 開始時に確認すること

1. 最新main、README、この記事運用手順、`docs/PUBLICATION_LOG.md`、未統合の変更を読む。取得したmainのSHAを保持する。
2. Zennの公開一覧と前回の結果を照合し、手動投稿や別の実行で完了した記事を重複投稿しない。
3. 「GitHub反映済み・Zenn未確認」の記事があれば、そのURLと本文を先に確認する。未確認のまま次の新作を重ねない。
4. 新規公開候補は公開記録の順に読み直す。古い検証結果だけで公開可と判断しない。

## 公開前の確認

- 冒頭で読者の困りごとと、この記事で分かることが伝わるか。
- タイトル、本文、サンプル、一次資料が同じ内容を説明しているか。
- 取得、固定版への切り替え、作業ディレクトリ、依存の導入、実行、期待結果まで読者がたどれるか。
- 実行を伴う主張は記事の対象範囲に合う既存の検証を動かす。実行環境、固定版、結果、限界を記録する。
- 構文抽出を型解決と扱う、fakeを実DB検証と扱うなど、検証範囲を超えた結論がないか。
- 引用元や再現コードのリンクが有効か。コードは可能な限りコミットへ固定する。
- front matter、見出し、表、コードブロックを確認する。公開に不要な情報を原稿へ含めない。

## 公開と完了条件

1. 選んだ原稿だけを公開対象へ変更し、最新mainとの競合を確認して反映する。GitHub APIの参照更新には取得したSHAを条件として使い、競合時は最新差分を読み直す。
2. この時点の状態は「GitHub反映済み・Zenn未確認」。反映commit、試行時刻、slug、公開URLを記録する。
3. Zennの公開URLを開き、タイトルと本文の特徴的な箇所、修正した手順が一致していることを確認する。HTTP 200、GitHub更新、デプロイ成功だけで完了としない。
4. ログイン不要で本文を読めることが確認できたら「Zenn公開確認済み」にする。READMEの公開一覧・本数・公開待ちを更新する。
5. 最終報告には公開URL、改善した内容、検証結果、次の候補、未完了があればその理由を簡潔に記載する。

## 投稿数制限や同期失敗がある場合

Zenn公式FAQでは記事は直近24時間の投稿数で判定され、予約投稿も含む。上限件数・ロジックは非公開。

- エラーや制限が明示されたら、その内容と時刻を記録し、同じ実行内で繰り返し投稿しない。
- 別slugへの複製や予約への変更で制限を回避しない。
- 次の点検枠では、同じslugの公開状態を最初に確認する。必要な場合に正規の再反映を1回行う。
- 「時間が経てば自動公開される」「25時間で必ず解除される」とは扱わない。
- 公開URLへアクセスできないだけで、投稿数制限と決めつけない。同期状態を観測できなければ「公開未確認」と記録する。
- 公開済みの記事を再公開のために下書きへ戻さない。未公開が確認された候補を待機へ戻す場合は、他の記事や手動変更と競合しないことを確認する。

## 公開候補が尽きた場合

既存の公開プロジェクトで実際に得られた変更・失敗・比較・検証から、次の読者の疑問を選ぶ。既存記事で十分説明されている場合は、更新内容だけをその記事へ反映する。新規性や確認できる証拠が不足する場合は、検証または下書きの整備まで進め、投稿枠を埋めるための新作を作らない。
