# Zennの編集・公開運用

## 対象と基本方針

- 対象は `RollNuts/zenn-content` と Zenn `veripsa`。2026年11月12日の依頼「zennを運用して、記事投稿して」に基づく。
- Git、Python、静的サイト、コード解析など、本人の公開プロジェクト・実際の実装・検証記録を題材にする。
- 追加費用は0円。既存の環境と無料の公開手段を使い、有料API、追加クレジット、従量課金を導入しない。
- 1記事につき読者の疑問を1つに絞る。既存記事と同じ説明を新作へ分割せず、既存記事の改善が適する場合は改稿する。
- 本人が経験していない体験、測っていない数値、未公開機能の利用実績を作らない。エージェントが実行した検証はそのように扱い、AI補助の開示を維持する。
- 2026年11月13日の追加依頼により、公開後の独立レビューを必須にする。第一の目標は読者の閲覧と回遊を増やすこと。収益化は読者の反応が確認できたテーマから育てる。

## 点検枠

火曜・土曜の19時ごろ（Asia/Tokyo）を基本とする。1回につき新規公開は最大1本。枠が来ても、題材・検証・独自の知見が不足する場合は既存原稿の改善に使う。

新しい公開・予約は、直近の公開または予約作成から25時間以上空いている場合だけ試す。これは余裕を持たせた独自の運用基準であり、Zennの投稿可能数や解除時刻を保証しない。

## 開始時に確認すること

1. 最新main、README、この記事運用手順、`docs/PUBLICATION_LOG.md`、未統合の変更を読む。取得したmainのSHAを保持する。
2. Zennの公開一覧と前回の結果を照合し、手動投稿や別の実行で完了した記事を重複投稿しない。
3. 「GitHub反映済み・Zenn未確認」または「公開後レビュー未完了」の記事があれば、その確認・レビュー・修正を先に行う。未確認のまま次の新作を重ねない。
4. 新規公開候補は公開記録の順に読み直す。古い検証結果だけで公開可と判断しない。

## 公開前の確認

- 冒頭で読者の困りごとと、この記事で分かることが伝わるか。
- タイトル、本文、サンプル、一次資料が同じ内容を説明しているか。
- 取得、固定版への切り替え、作業ディレクトリ、依存の導入、実行、期待結果まで読者がたどれるか。
- 実行を伴う主張は記事の対象範囲に合う既存の検証を動かす。実行環境、固定版、結果、限界を記録する。
- 構文抽出を型解決と扱う、fakeを実DB検証と扱うなど、検証範囲を超えた結論がないか。
- 引用元や再現コードのリンクが有効か。コードは可能な限りコミットへ固定する。
- front matter、見出し、表、コードブロックを確認する。公開に不要な情報を原稿へ含めない。

## 公開と完了条件

1. 選んだ原稿だけを公開対象へ変更し、最新mainとの競合を確認して反映する。GitHub APIの参照更新には取得したSHAを条件として使い、競合時は最新差分を読み直す。
2. この時点の状態は「GitHub反映済み・Zenn未確認」。反映commit、試行時刻、slug、公開URLを記録する。
3. Zennの公開URLを開き、タイトルと本文の特徴的な箇所、修正した手順が一致していることを確認する。HTTP 200、GitHub更新、デプロイ成功だけで完了としない。
4. ログイン不要で本文を読めることが確認できたら「Zenn公開確認済み」にする。公開後レビューの状態は別に保持し、この実行内で次節のレビューを行う。
5. レビューで見つかった重大な誤りや読者が詰まる点を修正し、公開ページに反映されたことを確認する。READMEの公開一覧・本数・公開待ちとレビュー記録を更新する。
6. 最終報告には公開URL、指定したレビュー用モデル、主要な指摘と修正、検証結果、取得できた読者指標、次の候補、未完了があればその理由を簡潔に記載する。

## 公開後の独立レビュー（必須）

公開確認の直後に、執筆担当とは別のレビュー担当へ公開URLと実際に反映した原稿を渡す。レビューには、追加費用0円の範囲で利用できる最高能力のモデルを明示指定する。

2026年11月13日時点では、公開後レビューの指定は `gpt-6-astra`、reasoning effortは `ultra`。独立したコンテキストで、本文・一次資料・再現条件を照合する。このモデルを指定した実行が受け付けられ、レビュー結果が返ったことを確認して記録する。今後、より高能力のモデルが公式資料と利用可能な選択肢の両方で確認できた場合は、その時点で選択を見直す。

定期タスク本体のモデル設定と、レビュー担当へのモデル指定は区別する。プロンプトにモデル名を書いただけで、本体のモデルを固定したと報告しない。指定機能がない、モデル指定が拒否された、または実行結果を得られなかった場合は「指定モデルでのレビュー未完了」と記録し、黙って下位モデルの結果を最高能力モデルの結果として扱わない。実施できる確認と修正は進め、未完了レビューは次回の優先対象にする。

レビューでは次を確認する。

1. 検索で来た初見の読者が、タイトルと冒頭から対象・悩み・得られる結果を判断できるか。
2. 必要な前提、取得手順、実行場所、依存、期待結果がそろい、途中で詰まらないか。
3. 主張が一次資料と実測に対応し、未確認の性能・効果・成功率を断言していないか。
4. 実際の公開画面で見出し・表・コード・リンクが読めるか。確認者と確認範囲を記録する。
5. 本文が問いに答えた後に、用途のつながる関連記事を最大2本案内できるか。関連が弱いリンクで埋めない。

重大な事実誤り・壊れた手順は先に直す。閲覧改善のための変更は1回のレビューで主要な仮説を1つに絞り、関連する修正箇所と日時を記録する。修正が広範囲の場合は差分をレビュー担当へ戻す。

## ビューを優先した改善

- 題材は、読者の具体的な困りごと、試しやすさ、既存記事との違い、手元で示せる結果から選ぶ。検索数や流行を調べていない場合は「編集上の仮説」と明記する。
- まず無料記事で、読者が自分でも確かめられる短い入口を増やす。タイトルで約束した内容を本文で実現し、未計測の効果でクリックを誘わない。
- 定期枠では公開後7日・28日を過ぎた記事の結果も確認する。同じ経過日数・同じ集計範囲でPVを比較し、公開直後の露出と長期の閲覧を混同しない。
- 記事別PV、取得期間、累計か期間値か、取得日時、取得元をセットで残す。取得できる場合のみ検索・外部流入、フォロー、関連リンクのクリックなども確認する。
- PV、読了率、検索表示数、クリック率を取得できなければ「未取得」とし、いいね数や推測で置き換えない。認証・アクセス・計測設定の不足を分けて記録する。
- リンク先のPVが増えただけで、関連記事導線の効果と断定しない。観測と因果の仮説を分ける。
- 管理画面で取得した非公開のPV・収益データを公開リポジトリへ転記しない。必要な集計は非公開の記録とユーザーへの報告で扱う。公開リポジトリには変更内容と検証条件を残す。

## 将来の収益化

Zennが案内する直接の収益手段は、有料の本と読者の有料バッジ。PVから収益を自動換算せず、実際の販売・バッジの記録を別に確認する。

最初は無料記事の閲覧、継続した読者の反応、具体的な質問を集める。同じテーマで説明を深める需要が見えたら、実行教材・失敗例・確認手順を体系化した本の企画へ進む。無料記事の単純な再包装は避け、読者が追加で得られるものを明確にする。読者の需要や売上が未確認の段階では、販売成立や将来の収益額を実績として扱わない。

## 投稿数制限や同期失敗がある場合

Zenn公式FAQでは記事は直近24時間の投稿数で判定され、予約投稿も含む。上限件数・ロジックは非公開。

- エラーや制限が明示されたら、その内容と時刻を記録し、同じ実行内で繰り返し投稿しない。
- 別slugへの複製や予約への変更で制限を回避しない。
- 次の点検枠では、同じslugの公開状態を最初に確認する。必要な場合に正規の再反映を1回行う。
- 「時間が経てば自動公開される」「25時間で必ず解除される」とは扱わない。
- 公開URLへアクセスできないだけで、投稿数制限と決めつけない。同期状態を観測できなければ「公開未確認」と記録する。
- 公開済みの記事を再公開のために下書きへ戻さない。未公開が確認された候補を待機へ戻す場合は、他の記事や手動変更と競合しないことを確認する。

## 公開候補が尽きた場合

既存の公開プロジェクトで実際に得られた変更・失敗・比較・検証から、次の読者の疑問を選ぶ。既存記事で十分説明されている場合は、更新内容だけをその記事へ反映する。新規性や確認できる証拠が不足する場合は、検証または下書きの整備まで進め、投稿枠を埋めるための新作を作らない。
